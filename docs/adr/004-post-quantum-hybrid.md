# ADR-004: Post-quantum гибрид (X25519 + ML-KEM-768) для сообщений

- **Статус:** Accepted, код-полон И **АКТИВИРОВАН**. Трек 1 (ECIES-гибрид room-key: DM/группы/voice/stories) — `vortex_pq_hybrid_enabled` переключён на **default-on** (opt-out kill-switch `='0'`) pre-launch (приложение не в сети, нет оператора). Multi-device лок-аут K5(b) неактуален: `key_backup.js:_collectKeyBundle` портирует аккаунтный Kyber-priv в тандеме с X25519-priv вне `includeEd25519`-гейта — на key-backup И device-linking; ⟹ каждое устройство с X25519-priv несёт Kyber-priv. Гейт `pq-hybrid.spec.js` — ЗЕЛЁНЫЙ на Firefox+Safari+Chrome. Приём — всегда-вкл. Трек 2 (PQXDH для v2 DR) — **сделан отдельным [ADR-006](006-pqxdh-double-ratchet.md), тоже активирован**.
- **Связано:** [ADR-001](001-message-encryption-versions.md) (enc_v-реестр), [ADR-002](002-multi-device-v2-sesame.md) (v2 Sesame X3DH — тоже не PQ, трек 2), [ADR-003](003-device-account-binding.md) (аккаунтный Ed25519 — им подписываем Kyber-pub).
- **Тип:** дизайн + план. Код по батчам, каждый дормантный/реверсивный, с advisor-чеком и real-browser гейтом перед активацией — как трек Sesame.

## 1. Находка (проверено по коду, не по утверждению)

PQ-защита сообщений в вебе **отсутствует де-факто**, и хуже — существующий PQ-код нефункционален и небезопасен:

- Клиентский `eciesEncrypt` (`static/js/crypto.js`) — **X25519-only**, без Kyber. Обёртка комнатных ключей везде через него (`contacts.js` DM, `rooms/keys.py` группы, `stories.js`, `voice_channel.js`, `key_backup.js`).
- `hybrid_ecies_encrypt` (`key_exchange.py:212`) корректен, но имеет **0 вызовов** — мёртвый код.
- При регистрации **СЕРВЕР** генерит Kyber-пару (`password.py:194`, `Kyber768.keygen()`), хранит `kyber_public_key`, а приватный `kyber_secret_key_hex` **вычисляется и выбрасывается** (не возвращается клиенту, не хранится). ⟹ у всех пользователей на сервере лежит `kyber_public_key` с **потерянным приватным** — нерасшифровываемый мусор. Плюс это E2E-нарушение (сервер видел приватный).
- Kyber реален только серверно (`post_quantum.py` через `liboqs-python`) + для **node-ключей** (`keys.py`, федерация). PQ-бейдж в UI (`chat-ux.js`) декоративен.

**Модель угроз: HNDL (harvest-now-decrypt-later) под A1.** Даже honest-but-curious сервер (или сетевой наблюдатель) может собирать сегодня зашифрованный трафик и расшифровать позже квантовым компьютером. Гибрид X25519+ML-KEM закрывает это: классическая часть держит сегодня, PQ-часть — против будущего кванта. Активный сервер (Б2) — вне скоупа, как везде.

## 2. Несущий инвариант (проверено): user-directed PQ — ЧИСТО client↔client

Обёртка комнатных ключей — E2E: отправитель-клиент оборачивает, получатель-клиент разворачивает, сервер релеит **opaque blob**. Проверено: в `app/chats/` и `app/keys/` **нет** серверного `ecies_decrypt`/`hybrid_decrypt` на user room-key blob'ах (серверный hybrid — только node↔node). ⟹

- **Клиент и отправитель, и получатель** → нужна ОДНА либа, self-consistency тривиальна.
- **НЕ матчим серверный формат** `hybrid_encrypt`. Крукс: liboqs `Kyber768` (round-3 кандидат) и `ML-KEM-768` (FIPS 203) — **разные, несовместимые** алгоритмы. Матчинг заставил бы клиент на серверный вариант ради НУЛЕВОГО E2E-выигрыша и втащил бы кросс-язычную byte-parity ловушку (та, что кусала на DH). Берём чистый **pure-JS ML-KEM-768**, кросс-язычного вектора нет.
- Инвариант **несущий**: если появится серверный путь, декриптящий user-directed hybrid blob, — этот ADR ломается. Не добавлять такой путь.

## 3. Решения

1. **Примитив — pure-JS ML-KEM-768 (FIPS 203), self-contained ESM.** CSP строгая: без CDN, без `wasm-unsafe-eval` (WASM-liboqs исключён). Кандидат — `@noble/post-quantum` (`ml_kem768`): pure-JS, аудируемый, вендорится одним ESM-файлом. Батч K1 проверяет вендоринг без build-шага.
2. **Client-side keygen (E2E).** Убрать серверную Kyber-keygen (`password.py`). Клиент генерит Kyber-пару, приватный — **долговременная per-account идентичность** как аккаунтный Ed25519: слот `vortex_kyber_priv_<userId>`, `_enc`-персистенция паролем (переживает logout, не форкается на login — переиспользуем дисциплину 0-bis), wipe-список. Размер приватного ML-KEM-768 ~2.4 КБ.
3. **Аутентичность Kyber-pub.** Отправитель фетчит Kyber-pub получателя с сервера — под A1 честно, но новый долговременный публичный ключ не должен иметь аутентичность слабее соседних. **Подписываем Kyber-pub аккаунтным Ed25519** (как SPK/identity_key в prekey-бандле), проверяем на отправке.
4. **Версионированный формат обёртки + классический fallback.** Обёрнутый ключ сейчас `{ephemeral_pub, ciphertext}`. Гибрид добавляет `kyber_ciphertext` + маркер версии. `shared = HKDF(x25519_shared ‖ kyber_shared, info)`. Получатель без (валидного, пост-миграционного) Kyber-pub → **классический X25519** (обратная совместимость). Реестр версий обёртки — рядом с enc_v-дисциплиной ADR-001.
5. **Real-capability detection (блокер).** «Есть Kyber-pub» ≠ «может расшифровать» (легаси-мусор). Отправитель гибрид-оборачивает ТОЛЬКО к **пост-миграционному** Kyber-pub (клиент-ген, подписанный). Тот же урок, что M3.3/M4b.
6. **Миграция легаси-ключей (предусловие, не afterthought).** На деплое **обнулить все серверные `kyber_public_key`** (мусор, downgrade-риска нет — приватного и так нет). Клиенты регенерят client-side и републишат. Порядок раскатки как у v2: получатели републишат ДО того, как отправители начнут таргетить (иначе гибрид к не-мигрированному → классика, безопасно, но без PQ).

## 4. Батчи (трек 1 — ECIES room-key path; «ECIES сначала»)

Каждый дормантный/реверсивный; активация — отдельным гейтом.

- **K1 — вендоринг ML-KEM-768 + KEM-примитив + round-trip — СДЕЛАНО (дормантно).** Вендорен `@noble/post-quantum@0.6.1` `ml_kem768` (= ML-KEM-768 FIPS 203) в self-contained ESM `static/js/vendor/mlkem768.js` (esbuild-бандл с `@noble/hashes`, 0 внешних импортов, ~28 КБ; регенерация — `vendor/README.md`). CSP-чист: 0 `eval`/`new Function`/`WebAssembly`, randomness через `globalThis.crypto` — `unsafe-eval`/`wasm-unsafe-eval` НЕ нужны. Обёртка `static/js/dr/mlkem.js` (`mlkemKeygen/mlkemEncaps/mlkemDecaps`, hex-API, размеры pk1184/sk2400/ct1088/ss32). Round-trip jest (`mlkem.test.js`): сходимость shared secret + implicit rejection при чужом приватном. `@noble/post-quantum` — devDependency (нужен только для регенерации вендора). Прод-код импортирует ТОЛЬКО wrapper. Реальная CSP-загрузка в браузере — на гейте K5 (Playwright).
- **K2 — lifecycle Kyber-ключа — СДЕЛАНО (дормантно).** `kyber-identity.js`: client keygen (E2E — сервер не видит приватный), load-only (не форкается на login), генерация только при регистрации; слот `vortex_kyber_priv_<userId>` (приватный hex, pub выводится из него). `_enc`-персистенция (`identity-persist.js` `saveKyberEnc/restoreKyberEnc`, PBKDF2 600k+AES-GCM — та же дисциплина 0-bis). `signKyberPub` — pub подписан аккаунтным Ed25519. auth.js-обвязка (регистрация: keygen+`_enc`+publish; login: restore+publish; logout: wipe плейнтекста, `_enc` переживает; removeAccount: полное удаление). Сервер: **убрана серверная keygen** (`password.py` — она видела приватный и выбрасывала его); эндпоинт `POST /api/keys/kyber` (`kyber_public_key`+`kyber_public_key_sig`, колонка `kyber_public_key_sig` на User); профиль отдаёт оба. Обнуление легаси серверных ключей — на деплое (§3.6, K5). Тесты: `kyber-identity.test.js` (7: не форкается, `_enc` переживает logout, подпись верифицируется), `test_kyber_publish.py` (2). Регрессии нет (auth.test.js 21 failed — пре-существующие, +0 от K2).
- **K3 — версионированный hybrid wrap/unwrap + классический fallback — СДЕЛАНО (дормантно).** `hybridEciesEncrypt/hybridEciesDecrypt` в `crypto.js`: комбинатор `ikm = x25519_shared ‖ kyber_shared` → `HKDF-SHA256(info="vortex-pq-hybrid-v2")` → AES-256-GCM (домен-сепарация от классического `"vortex-session"`). Формат-версия: гибрид `{v:2, ephemeral_pub, kyber_ct, ciphertext}`, классика `{ephemeral_pub, ciphertext}` (без v); decrypt роутит по конверту (обратная совместимость). **Fallback:** нет Kyber-pub у получателя → `eciesEncrypt` (X25519-only). ML-KEM грузится **лениво** (вендор ~28КБ — только на гибрид-операции; дормантно до K4/K5). Тест `crypto-hybrid.test.js` (5): round-trip между РАЗДЕЛЬНЫМИ сторонами (отправитель — только pub, получатель — только priv), классический fallback, неверный Kyber/X25519-priv → AEAD-провал, гибрид без Kyber-priv → явная ошибка. Не подключён к call-sites обёртки (K4).
- **K4 — real-capability detection + провязка в обёртку. РЕФОРМИРОВАН (advisor-чек): это client + SERVER-SCHEMA, не client-only.**
  - **Находка (проверено):** обёрнутый ключ хранится/релеится ДИСКРЕТНЫМИ полями `{ephemeral_pub, ciphertext}` (модель `EncryptedRoomKey` — колонки; строгие Pydantic-схемы `EncryptedKeyPayload`/store-key/group/sealed; `validate_ecies_payload`). Для `kyber_ciphertext` места нет → Pydantic его отбросит → **тихий провал** (получатель видит классический-с-виду конверт с потерянным kyber → декрипт как классика → AES-ключ был гибридным → InvalidTag). ⟹ каждый путь wrap→store→relay→unwrap обязан нести `kyber_ciphertext` + маркер `hybrid`.
  - **K4-prep — СДЕЛАНО:** формат гибрид-конверта выровнен под серверный `validate_ecies_payload` (`{hybrid:true, x25519_ephemeral_pub, kyber_ciphertext, ciphertext}`; классика `{ephemeral_pub, ciphertext}`) — переиспользует существующую валидацию, минимизирует server-schema-дивергенцию. (KEM-контент — мой ML-KEM-768; сервер его НЕ декапсулирует, только релеит — инвариант §2 цел.) `crypto-hybrid.test.js` обновлён.
  - **Порядок (advisor):** приём — ВСЕГДА-ВКЛ (все unwrap-сайты: `websocket.js`, `notifications.js`, `zk-crypto.js`, `crypto.js` внутр. — через `hybridEciesDecrypt` + прокидка своего Kyber-priv) ДО того, как любой отправитель включит флаг. Отправка — за флагом `vortex_pq_hybrid_enabled` (дефолт ВЫКЛ, флип на K5), как v2-активация. **Load-bearing — приём (все сайты).**
  - **Capability (advisor, reuse не invention):** DM `other_user` уже несёт `kyber_public_key` — добавить `kyber_public_key_sig`; проверять подпись против `pinnedPeerAccountEd` (identity-pin.js, M3.2a — тот же TOFU-пин v2-пути); нет пина → fetch-and-pin-on-first-use (как v2). Под A1 после K5-обнуления «pub есть» = функциональный флор; подпись = Б2-аутентичность.
  - **Под-батчи:** K4a — server-schema: `kyber_ciphertext` колонка/поля через DM-путь (`EncryptedRoomKey` + схемы + релей, аддитивно/backward-compat/дормантно); K4b — приём-все-сайты (всегда-вкл); K4c — отправка (флаг) + capability; K4d — group/voice + key_request-ответ; K4e — stories (контакт-pubkey поверхность); sealed prekeys — УДАЛЕНЫ (механизм был сломан: one-time приватный выбрасывался → недекриптуемо + глушило key_request).
  - **K4a — СДЕЛАНО:** `EncryptedRoomKey.kyber_ciphertext` (Text, nullable) + ALTER (идемпотентный, duplicate-column глотается); `to_client_dict()` отдаёт гибрид-форму при наличии kyber_ciphertext, иначе классику. Дормантно (клиент ещё не шлёт гибрид). `test_dm_hybrid_key.py`: гибрид переживает store→fetch (в т.ч. для получателя, ветка `encrypted_key_for_target`), классика цела (backward-compat), битая форма → 422.
  - **K4b — СДЕЛАНО:** приём всегда-вкл. Хелпер `decryptRoomKeyEnvelope(envelope, x25519PrivJwk)` (crypto.js) роутит по конверту: гибрид → подхватывает аккаунтный Kyber-priv текущего пользователя (`loadKyberIdentity(AppState.user.user_id)`, load-only, dynamic-import) → `hybridEciesDecrypt`; классика → без Kyber (обратная совместимость). Провязан во все unwrap-сайты комнатного ключа: `websocket.js` (`_pullKeyFromServer` key-bundle + `case 'room_key'`), `notifications.js` (`_handleRoomKeyFromNotif`), `zk-crypto.js` (`_fetchBlindKey`). Гарды приёма расширены на `x25519_ephemeral_pub` (иначе гибрид-конверт молча отбрасывался). Устройство без локального Kyber-priv на гибрид-конверте → явная ошибка (K5-edge: подавить capability/републиш). **BMP-путь (blind mailbox) покрыт транзитивно:** серверный JSON-депозит `{type:'room_key',…}` при poll'е парсится, `_typeToCode('room_key')`∉`_TYPE_MAP`→`MSG.MESSAGE`→`_bmpMsg`→`handleWsMessage`→ тот же конвертированный `case 'room_key'`; отдельного inline-decrypt для room_key в bmp-client.js нет (unpackEnvelope-путь требует уже известный room_key — не применим к его доставке). `crypto-room-key-envelope.test.js`: классика без Kyber/AppState, гибрид из слота юзера, нет идентичности → ошибка, чужой Kyber → AEAD-провал.

X25519-priv едет в key_backup-бандле; Kyber-priv — НЕТ (только same-device `_enc`) → гибрид залочил бы восстановленные устройства. Kyber добавлен в бандл (`kyber_private_hex`, `_collectKeyBundle`/`_restoreKeyBundle`) в **тире X25519, вне гейта `includeEd25519`** (KEM-ключ не подписывает — blast-radius линковки ADR-003 §3.3 не применим; портируется и на залинкованные устройства). Тесты: `pq-capability.test.js` (7 — флаг, verify против пина, fetch-and-pin, чужая подпись, self), `key-backup-kyber.test.js` (2 — cross-device round-trip backup→restore→расшифровка гибрида; старый бандл без Kyber не падает), `test_dm_hybrid_key.py::test_dm_other_user_carries_kyber_pub_sig`.
  - **K4d — СДЕЛАНО (T1 + T2; sealed/stories отложены с обоснованием):**
    - **Единая схема:** три копии ECIES-схемы (dm.py `_EciesKeyFields`, helpers.py `EncryptedKeyPayload`, channels.py `_EncryptedKeyPayload`) сведены в общую `app/security/ecies_schema.py::EciesKeyFields` (обе формы + валидатор + `eph_pub`/`ecies_dict()`). Провязка kyber_ciphertext в group create-store: `rooms/crud.py`, `channels.py`.
    - **T1 — group/voice self-key гибрид (за флагом):** create room/channel (`rooms/core.js`), voice (`voice_channel.js`), key-rotation self-wrap (`websocket.js`) → `hybridEciesEncrypt(rk, myPub, myKyberPub())`. Хранится в `EncryptedRoomKey` (K4a/b готовы). `test_room_hybrid_key.py`: room+channel create-hybrid переживает store→fetch, классика цела.
    - **T2 — key_request-ответ гибрид (закрывает K4c-gap (d) + ВСЕ групповые peer-ключи одним ходом; путь общий DM+group через dm/store-key):** сервер протягивает `for_kyber_pubkey`+`for_kyber_sig` реквестера через КАЖДЫЙ эмиттер key_request (`_broadcast_key_request` helpers.py; `deliver_or_request_room_key` room-broadcast+notify+BMP и `notify_pending_key_requests` messages/keys.py — через `_kyber_req_fields`; rooms/keys.py join+rekey). `handle_key_response` (WS-fallback) сделан гибрид-полным (приём обеих форм, store с kyber, релей гибрид-формой). Клиент (`websocket.js case 'key_request'`, `notifications.js`) → `resolvePeerKyberPub(for_user_id, for_kyber_pubkey, for_kyber_sig)` + `hybridEciesEncrypt`. **Инвариант доверия:** pub из broadcast НЕ доверенный — `resolvePeerKyberPub` проверяет подпись против припиненного/фетч-энд-пин Ed реквестера; без подписи → классика (не сломано, приём универсален K4b).
    - **Sealed prekeys — УДАЛЕНЫ (не гибрид, а починка сломанного):** `_uploadSealedPrekeys` оборачивал room key на one-time X25519 pubkey и **выбрасывал приватный** → пакеты недекриптуемы; хуже — авто-claim в `deliver_or_request_room_key` создавал сломанный `EncryptedRoomKey` (has_key=True) и `return`, навсегда глуша рабочий key_request. Механизм несалважим E2E (нельзя обернуть на ключ неизвестного будущего участника; anonymous+offline+E2E — противоречие). Удалено: consumer-блок (messages/keys.py → fall-through к key_request), эндпоинты (`sealed_keys.py` upload/claim/count), клиентский `_uploadSealedPrekeys`+все вызовы+`prekeys_low` цикл. Модель/таблица `SealedKeyPackage` оставлены дормантно (panic-ref) — и переиспользованы для heal'а. Heal-миграция: удаляет отравленные `EncryptedRoomKey` через **JOIN против `sealed_key_packages`** по (room_id, ephemeral_pub, ciphertext) — старый consumer копировал их дословно, случайные ephemeral+nonce не коллизят → ноль false-positive, независимо от recipient_pub/escrow/rotation (advisor: строго лучше recipient_pub-эвристики). ## 5. Трек 2 — v2 Sesame PQXDH (после трека 1)

Kyber в X3DH живых 1:1 DM (Signal PQXDH-стиль): recipient публикует Kyber-pre-key (подписанный, как SPK); инициатор энкапсулирует, `shared = HKDF(DH1‖DH2‖DH3[‖DH4]‖kyber_shared)`; wire-формат прелюды расширяется (kyber_ciphertext) — та же byte-parity/skew-дисциплина, что M3.2c. Отдельный ADR-раздел/батчи; фундамент K1–K2 переиспользуется (та же ML-KEM-либа + Kyber-lifecycle, но Kyber-pre-keys, не аккаунтный Kyber).

## 6. Не-цели / вне скоупа

- Серверный hybrid node↔node (`key_exchange.py`, федерация) — НЕ трогаем (отдельная граница; там кросс-язычность к liboqs — свой вопрос).
- Активный сервер (Б2) — вне скоупа проекта (подмена Kyber-pub на фетче; safety-number/подпись Ed25519 — граница A1, как везде).
- Secret-shares / federated backup shards (`key_backup.js`) — recovery-путь, не сообщения; PQ там — опционально, позже.
