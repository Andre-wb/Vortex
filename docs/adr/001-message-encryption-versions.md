# ADR-001: Версионирование шифрования сообщений и целевая архитектура Double Ratchet

- **Статус:** Proposed
- **Дата:** 2026-07-09
- **Область:** шифрование текстовых сообщений комнат (WS-путь `action: "message"` и производные: edit, thread, captions)
- **Не затрагивает:** медиапоток звонков (`e2e_media.js`, HKDF info `vortex-media-e2e`), транспортный BMP-конверт (`bmp-envelope.js`, HKDF info `bmp-envelope`, собственный байт версии), шифрование файлов и историй

## 1. Контекст

Продовое шифрование сообщений выполняется на клиенте в `static/js/crypto.js`:

- `ratchetEncrypt`/`ratchetDecrypt` (crypto.js:314, crypto.js:346) — симметричная HKDF-цепочка на отправителя (`roomId:senderId`), **засеянная напрямую постоянным roomKey** (`initRatchet`, crypto.js:306).
- При рассинхроне счётчика или ошибке расшифровки цепочка молча переинициализируется из roomKey с counter=0 (crypto.js:372, crypto.js:396–409).
- Параллельно существует legacy-формат — прямой AES-256-GCM на roomKey: голый `nonce+ct` (`_legacyDecrypt`, crypto.js:432) и padded-вариант с magic `0x5678` (`room-crypto.js:19,66`).
- **Поля версии протокола нет нигде**: ни в WS-конверте (`send.js:126` передаёт только `ciphertext` hex), ни в модели `Message` (`app/models_rooms/messages.py` — `content_encrypted LargeBinary`, без колонки алгоритма). Форматы различаются эвристикой по длине и величине первых 4 байт (`counter > 100000` → legacy, crypto.js:349, crypto.js:356).

Следствия для свойств безопасности:

- **Forward secrecy фактически отсутствует**: seed цепочки (roomKey) постоянен и хранится рядом с состоянием (localStorage/sessionStorage, crypto.js:132–150). Компрометация устройства восстанавливает все прошлые сообщения повторной прогонкой цепочки от seed.
- **Post-compromise security / break-in recovery отсутствует**: DH-ратчета нет; узнав roomKey, атакующий читает всё будущее без переустановки ключей.

Смежная инфраструктура, на которую опирается миграция:

- `app/security/double_ratchet.py` — полная референс-реализация X3DH + Double Ratchet (Header 40 байт как AAD, kdf_rk/kdf_ck, skipped-keys c MAX_SKIP=1000, сериализация состояния). **Мёртвый код**: в проде не импортируется. Роль в миграции — спецификация и генератор кросс-языковых тест-векторов; продовый ратчет обязан исполняться на клиенте.
- Серверное хранилище X3DH уже смонтировано: `PreKeyBundle`/`OneTimePreKey` (`app/models/prekeys.py:25,74`), эндпоинты `/api/keys/prekeys/*` (`app/keys/prekeys.py:103,193,268`, mount `app/main.py:757-758`). Клиентских вызовов нет; подпись SPK сервером не проверяется.
- Identity-ключи пользователя: только X25519 (`User.x25519_public_key`, `app/models/user.py:38`); приватный ключ — JWK-строка в localStorage/sessionStorage (`auth.js:77-78`), опционально passphrase-encrypted копия (`auth.js:88-89`). Ed25519-идентичности на клиенте нет.
- Сервер полностью opaque к шифртексту: валидирует hex и длину 48–65536 hex-символов (`app/chats/messages/messages.py:163,170`), считает BLAKE3-хэш. Федерация (`federation.py`, `replication.py`) релеит payload как непрозрачный JSON.

## 2. Решение

### 2.1. Реестр версий протокола (`enc_v`)

Вводится целочисленное поле `enc_v` — идентификатор схемы шифрования сообщения.

| `enc_v` | Название | Схема | Формат `ciphertext` (hex) | Статус |
|---|---|---|---|---|
| 0 | legacy | Прямой AES-256-GCM на roomKey (голый или padded c magic `0x5678`) | `nonce(12) + ct` | Существует. Только чтение; новыми клиентами не отправляется |
| 1 | sender-chain | Симметричная HKDF-цепочка, seed = roomKey; msgKey = HKDF(chainKey, "msg-key"), advance = HKDF(chainKey, "chain-advance") | `counter(4 BE) + nonce(12) + ct` | Текущий формат отправки |
| 2 | pairwise-dr | X3DH-установка + Double Ratchet (DH-ратчет X25519, kdf_rk/kdf_ck, Header как AAD) по образцу `double_ratchet.py` | `header(40: dh_pub(32) + pn(u32 BE) + n(u32 BE)) + nonce(12) + ct` | Целевой для 1:1 (DM) |
| 3 | group-sender-keys | Пер-отправительская симметричная цепочка со **случайным эфемерным** seed, распределяемым по pairwise-v2-сессиям; re-key при изменении состава и по интервалу | `header + counter + nonce + ct` (уточняется в ADR батча 7a) | Целевой для групп |

Правила реестра:

1. Новые значения `enc_v` добавляются только через обновление этого ADR.
2. `enc_v` передаётся **полем JSON-конверта** WS-сообщения (рядом с `ciphertext`), а не байтом внутри шифртекста. Обоснование: поле аддитивно (старые клиенты игнорируют неизвестные ключи JSON), тогда как ведущий байт внутри hex сломал бы расшифровку у старых клиентов и текущую эвристику.
3. В БД `enc_v` хранится в nullable-колонке `Message.enc_version`; `NULL` = сообщение до введения версионирования.
4. Отсутствие поля в конверте / `NULL` в БД → расшифровка по существующей эвристике (crypto.js:349, crypto.js:356). При наличии поля оно имеет безусловный приоритет над эвристикой.
5. Неизвестная (более новая) версия: клиент показывает заглушку «сообщение в неподдерживаемом формате, обновите клиент» и не пытается расшифровать; сервер хранит и релеит opaque, не отклоняя.
6. Сервер никогда не парсит внутренности `ciphertext` и не участвует в криптографии сообщений; серверная валидация ограничивается hex/длиной/хэшем, как сейчас.

### 2.2. Таблица свойств (честная)

| Свойство | v0 | v1 | v2 | v3 |
|---|---|---|---|---|
| E2E-конфиденциальность против сервера (приватные комнаты) | да | да | да | да |
| Forward secrecy при компрометации состояния устройства | **нет** (roomKey расшифровывает всё) | **нет фактически** (цепочка выводима из постоянного seed, лежащего рядом) | да (ключи сообщений удаляются; DH-выходы невыводимы из снапшота) | да (эфемерные sender-seed'ы) |
| Post-compromise security / break-in recovery | нет | нет | **да** (DH-ратчет) | **да** на уровне группы (re-key через v2-каналы) |
| Устойчивость к тихой реинициализации из постоянного seed | — | **нет** (crypto.js:372,396 — переинициализация из roomKey это штатный путь) | да (реинициализация возможна только новым X3DH, видимым в протоколе) | да |
| Терпимость к out-of-order доставке | нет (нет счётчика) | частичная (только вперёд; откат = reset) | да (skipped-keys, лимит MAX_SKIP) | да |
| Отзыв доступа при выходе участника | нет (до ручного rotate-key) | нет (то же) | n/a (1:1) | да (re-key при изменении состава) |
| Криптографическая привязка prekey к идентичности | — | — | да (подпись SPK ключом Ed25519) | да |

Что **не** даёт ни одна версия (принимаемые ограничения, см. §4): защита от XSS в момент компрометации, защита метаданных сверх текущего `sender_pseudo`/BMP, защита от злонамеренного сервера, подменяющего prekey-бандлы целиком (до внеполосной верификации отпечатков), deniability-гарантии уровня Signal.

### 2.3. Модель угроз

Защищаемся (по нарастающей с версиями):

- **А1. Скомпрометированный/любопытный сервер** — читает БД и трафик, но действует пассивно: все версии (E2E).
- **А2. Разовая эксфильтрация состояния клиента** (снапшот localStorage/IndexedDB, бэкап устройства): v2/v3 — прошлое не восстанавливается (FS), будущее излечивается DH-ратчетом (PCS). v0/v1 — полная компрометация прошлого и будущего.
- **А3. Пассивный сетевой наблюдатель**: TLS + E2E, все версии.
- **А4. Бывший участник комнаты**: v3 — теряет доступ после re-key; v0/v1 — только через ручной `rotate-key`.

Не защищаемся (вне скоупа данной миграции):

- **Б1. Персистентный XSS / вредоносный код в клиенте** — читает плейнтекст и ключи в моменте. Частичная митигация (non-extractable CryptoKey в IndexedDB) — отдельный трек после батча 5.
- **Б2. Активно-злонамеренный сервер, подменяющий бандлы**: подпись SPK связывает prekey с identity-ключом, но сам identity-ключ пользователь получает от сервера. Полная защита требует внеполосного сравнения отпечатков (safety numbers) — кандидат в отдельный ADR.
- **Б3. Злонамеренный легитимный участник комнаты** — тривиально сливает плейнтекст; криптография тут бессильна.
- **Б4. Анализ метаданных** — за пределами существующих механизмов (sealed-sender-псевдонимы, BMP).

### 2.4. Дизайн-решения

**(а) Мультивкладка: single-writer.** DR-состояние сессии мутабельно; конкурентное продвижение ратчета из двух вкладок форкает сессию и необратимо ломает расшифровку. Решение: состояние сессий v2/v3 хранится в IndexedDB, все операции encrypt/decrypt для сессии выполняются под `navigator.locks` (Web Locks API) с per-session ключом блокировки; вкладка без блокировки ждёт, а не работает на копии. Синхронизация через BroadcastChannel (как у roomKey, crypto.js:104) для DR-состояния **запрещена** — она источник форков, а не решение.

**(б) Мультидевайс: вне скоупа v2/v3.** Сессии — пер-пользовательские (одна активная DR-сессия на пару пользователей), что соответствует фактической модели сегодняшнего клиента. Инфраструктура `UserDevice.device_pub_key` (`app/models/user.py:114`) и `DeviceLinkRequest` не задействуются в ратчете. Пер-девайсные сессии (аналог Sesame) — отдельный будущий ADR; здесь фиксируем только, что реестр `enc_v` и формат header их не блокируют.

**(в) Бэкап: DR-состояние не бэкапится.** В passphrase-vault (`key_backup.js`, `KeyBackup` c колонкой `version`, `app/models/user.py:141`) попадают: identity-ключи (X25519 + новый Ed25519) и legacy roomKey'и. **Не попадают**: состояния DR-сессий, цепочные и skipped-ключи — их бэкап уничтожает forward secrecy (архивная копия состояния позволяет расшифровать прошлое, ради невозможности чего DR и вводится). Потеря устройства ⇒ старые v2/v3-сообщения нечитаемы на новом устройстве — это осознанная цена FS, идентичная поведению Signal при смене устройства.

**(г) Идентичность: два ключа и их связывание (батч 4).** XEdDSA вне скоупа, поэтому долговременная идентичность — это **пара** ключей: X25519 `identity_key` (для DH в X3DH) и Ed25519 `identity_key_ed` (для подписей). Signed Pre-Key подписывается Ed25519-ключом (`signed_prekey_sig`). Дополнительно Ed25519-ключ подписывает X25519 `identity_key` (`identity_key_sig`) — cross-signature, связывающая два ключа в одну идентичность. Следствие: **отпечаток/safety-number идентичности обязан вычисляться по ПАРЕ (`identity_key`, `identity_key_ed`)**, а не по одному ключу — иначе внеполосная верификация покроет Ed25519-ключ, но не X25519-ключ, на котором X3DH выполняет DH (батч 6). Cross-signature гарантирует, что верифицированный Ed25519-отпечаток транзитивно authenticates X25519 DH-ключ.

Что батч 4 **не** даёт (важно для честности, ср. §2.3 Б2): серверная верификация подписей проверяет лишь целостность бандла относительно *опубликованного* Ed25519-ключа. Пока этот ключ не верифицирован внеполосно (safety-number), злонамеренный сервер/MITM-на-публикации может подменить всю пару целиком со своей подписью — verification пройдёт. То есть батч 4 поставляет **механизм и хранилище** верификации, но **не** substitution-resistance; последнее появляется только с внеполосной верификацией отпечатков (отдельный будущий трек).

### 2.6. Формат провода v2 (батч 6a)

`enc_v:2`, `ciphertext` (hex) — два типа сообщений (как PreKeySignalMessage / SignalMessage), реализация `static/js/dr/v2-envelope.js`:

```
[1]  type: 0x01 prekey (установление сессии) | 0x02 normal
если prekey:
  [32] initiator_identity_pub   (X25519 IK инициатора — вход X3DH-respond)
  [32] initiator_ephemeral_pub  (EK инициатора)
  [4]  spk_id (BE u32)          (какой Signed Pre-Key адресата)
  [1]  has_opk (0/1); если 1: [4] opk_id (BE u32)
[40]  dr_header (dh_public(32) + prev_count(u32 BE) + msg_number(u32 BE))
[..]  aead (nonce(12) + AES-256-GCM ct+tag)
```

- Сессия ключуется по roomId DM (`dm:<roomId>`); v2 применяется **только к `is_dm`** комнатам, вне DM — плейсхолдер.
- Прелюда **не** входит в AAD (AAD — только 40-байтный header). Отдельного MAC нет: подмена прелюды меняет выведенный root key → `ratchet_decrypt` падает `InvalidTag` (транзитивная защита).
- **Аутентификация инициатора — TOFU.** `sender_id` и IK в прелюде задаются отправителем; приёмник проверяет, что IK прелюды совпадает с опубликованным `x25519_public_key` отправителя (`identity_mismatch` иначе). Но пока этот ключ не верифицирован внеполосно (safety-number по паре, §2.4г), злонамеренный сервер может подменить пару целиком — v2 даёт FS/PCS против утечки состояния, **не** substitution-resistance. Реализация `static/js/dr/session.js`.
- Приватные Signed/One-Time Pre-Key адресата хранятся клиентом (`static/js/dr/prekey-store.js`, per-account); использованный OPK **удаляется** после установления (FS). Пользователи, опубликовавшие бандл в батче 4 (без локальных приватных), форсируют один republish; до него входящий v2 деградирует в плейсхолдер, не в краш.

### 2.7. Отправка v2 и capability (батч 6b)

- **Capability.** Бандл несёт `supports_v2` (столбец в `PreKeyBundle`, поля в publish/fetch/status). 6a+-клиент публикует `supports_v2:true`; отправитель шлёт v2 **только** если fetch адресата вернул `supports_v2===true`. Пред-6b/батч-4 бандлы (`NULL`) → отправитель падает в v1. Триггеры republish OR'ятся: нет приватных (`!hasPrekeyPrivates()` — self-heal при потере localStorage) ИЛИ `status.supports_v2!==true`.
- **Решение об отправке** (`encryptV2ForDm`, `static/js/chat/message-cipher.js`): применяется только к 1:1 DM, кэшируется на объекте комнаты (`_v2`: `yes`/`no`). Перед установлением отправитель проверяет: capability, TOFU (`identity_key` бандла == известный `x25519_public_key` адресата) и подписи бандла (`edVerify` SPK+binding — defense-in-depth против warn-only сервера). Любая окончательная причина → кэш `no` → v1; транзиентная (сеть) → повтор. Область: только основной message-путь; edit/schedule/timed/thread/стикеры остаются v1.

**Гейты на включение флага (код посажен «спящим», флаг по умолчанию ВЫКЛ):**

- **История v2 после перезагрузки — РЕШЕНО (локальный стор плейнтекста).** Проблема: Double Ratchet не может повторно расшифровать сообщение с израсходованным ключом, а Vortex перерасшифровывает историю из серверного шифртекста при каждом открытии комнаты (`case 'history'` → `_decryptAndAppend`). Решение (как message-DB в Signal): `static/js/dr/history-store.js` — при ПЕРВОЙ живой расшифровке плейнтекст кэшируется локально (`decryptV2WithHistory`, cache-first по `msg_id`); история и дубли доставки читаются из кэша, БЕЗ повторного расхода ключей ратчета. Плейнтекст не лежит в открытом виде: пере-шифрован AES-256-GCM под per-account локальным ключом (`vortex_dr_hist_key_<userId>`) — профиль совпадает с v1 (локальный ключ + шифртекст).
  - **Свои отправленные сообщения** нельзя расшифровать по receiving-цепочке (DR асимметричен), поэтому их плейнтекст кэшируется отдельно — под серверным `msg_id` по ACK (`cacheV2Sent`, `send.js`). На собственном эхе (`sender_id === me`) и после reload плейнтекст берётся из этого кэша (`getV2Cached`), а не транспортной расшифровкой. Живой эхо-рейс (эхо через BMP раньше ACK-put) редок (ACK эмитится сервером до BMP-депозита) и самолечится при переоткрытии комнаты.
  - Остаточный случай: чужое сообщение, ни разу не расшифрованное успешно (напр., ключ израсходован дублем при отсутствующем кэше) → плейсхолдер; сессия при этом не портится (`withSession` не делает `put` при throw).
  - Стор чистится при logout (IDB `vortex_v2_history` + префикс `vortex_dr_`) и removeAccount (удаление history-ключа делает кэш нечитаемым).
  - **Не блокирует, но зафиксировано:** (1) `history-store` открывает ВТОРУЮ IndexedDB (`vortex_v2_history`) через тот же непровалидированный `indexedDbBackend` — Playwright-гейт обязан упражнять и её (put → reload → get), не только session-store; (2) кэш истории **без границы вытеснения** — каждое v2-сообщение кэшируется навсегда (осознанный выбор; eviction/TTL — будущее).

- **Флаг — per-client opt-in, НЕ централизованный kill-switch.** `localStorage['vortex_v2_dm_enabled']='1'`. Выключение мгновенно возвращает v1-отправку у ЭТОГО клиента; уже отправленные v2 читаются всеми 6a+. Оператор не может остановить раскатку централизованно без деплоя — настоящий серверный kill-switch (флаг из конфига, который клиент и так тянет) — отдельный трек. Пока формулировка «per-client opt-in», а не «central kill-switch».
- **Мультидевайс (известное ограничение, регресс относительно v1) — решение в [ADR-002](002-multi-device-v2-sesame.md).** `supports_v2` и bundle — per-**user**, приватные prekey — per-**device**; из двух устройств аккаунта «другое» даёт `InvalidTag`→плейсхолдер на входящем v2 (v1 читался всеми через общий roomKey). Настоящий мультидевайс требует per-device сессий (Sesame) — короткого пути нет; interim «single-device гейт» нежизнеспособен (device-строки накапливаются). ADR-002 фиксирует развилку: строить Sesame (4 батча) либо оставить v2 спящим. **До выбора флаг не включать.**
- **Session-wedge (смягчён, остаточный риск).** Prekey-конверт производится один раз; далее только normal. `sendWithAck` durably ретраит (5 попыток + IndexedDB-очередь), сервер персистит сообщения (pending 7d) — так что первое сообщение почти наверняка дойдёт до адресата. Остаточный риск (сервер за-ACK'ал, но адресат его так и не получил) → сессия у адресата не установится (`no_session` плейсхолдер). Полное решение — «слать prekey-прелюду, пока не получено первое входящее в сессии» — будущее ужесточение.
- **IndexedDB/Web Locks не валидированы в браузере.** Playwright-гейт (`playwright-tests/tests/dr-session-store.spec.js`) должен пройти в реальном браузере до включения флага.

### 2.5. Сквозные принципы миграции

1. **Decrypt раньше encrypt**: поддержка чтения версии N раскатывается минимум на один релиз раньше первой отправки в ней.
2. **Отправка в новой версии — только по capability-переговорам** (адресат заявил поддержку) и за фичефлагом с kill-switch; выключение флага мгновенно возвращает предыдущую версию отправки, не ломая чтение уже отправленного.
3. **Чтение legacy (v0/v1) не удаляется никогда** — история должна оставаться читаемой. Деприкация касается только отправки и только после метрик покрытия (батч 8).
4. **Без заявлений о Signal-совместимости.** Используются конструкции из спецификаций Double Ratchet и X3DH (signal.org/docs), но: нет wire-совместимости, нет XEdDSA (SPK подписывается отдельным Ed25519-ключом), нет Sesame/мультидевайса, sealed sender остаётся текущим (`sender_pseudo`). Формулировка в документации и UI: «протокол на основе Double Ratchet».
5. Каждый батч мал, независимо ревьюируем и откатываем; изменения продовой криптографии начинаются не раньше батча 6b (до этого — только версионирование, тесты, абстракции).

## 4. Последствия и принятые риски

- Появляется постоянная стоимость: реестр версий и матрица совместимости клиентов, которую надо тестировать (v0/v1-история обязана читаться всеми будущими клиентами).
- v2/v3 вводят персистентное мутабельное состояние на клиенте (IndexedDB) — новый класс багов (форк сессии, потеря состояния). Митигируется решением 2.4(а) и тестами батча 5 (reload/конкуренция вкладок).
- FS означает реальную потерю данных при потере устройства (2.4(в)) — требует явного текста в UI бэкапа.
- Ограничения Б1–Б4 (§2.3) принимаются осознанно и не должны замалчиваться в пользовательской документации: до внеполосной верификации отпечатков доверие к identity-ключам упирается в сервер.
- Приватные ключи остаются в web-хранилище браузера; DR ограничивает ущерб *утечки снапшота*, но не *текущей* компрометации страницы.
