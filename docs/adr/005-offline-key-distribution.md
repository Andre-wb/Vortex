# ADR-005: Оффлайн-раздача комнатного ключа новому участнику

- **Статус:** Accepted, код-полон (O1–O7), дормантно за флагами; флип за оператором. **Трек 1 (pre-wrap directed-invite)** — `provision-key`/approve-join, за `vortex_offline_invite_enabled`. **Трек 2 (анонимный-линк escrow)** — O4–O7, за тем же флагом. Sealed prekeys — вне трека (удалены как сломанные).
  - **Остаток оператора (флип-чеклист):** (1) деплой (Postgres/Alembic → миграция 4 схем-изменений: `room_join_requests`, `room_invite_escrows`, `room_invites`, `room_invites.expires_at`); (2) зелёные браузер-гейты ≥ Chrome+Firefox (`pq-hybrid`, `offline-invite`, `invite-link`, `room-key-heal`); (3) убедиться: приём/self-heal/redeem раскатаны ВЕЗДЕ ДО флипа отправки; (4) флип `vortex_offline_invite_enabled='1'`; при утечке ссылки → revoke + ротация room key.
- **Связано:** [ADR-004](004-post-quantum-hybrid.md) (гибрид-обёртка ключей — переиспользуем всю K4-машинерию), [ADR-001](001-message-encryption-versions.md).
- **Тип:** дизайн + план. Код по батчам, каждый дормантный/реверсивный, с advisor-чеком и real-browser гейтом перед активацией — как трек ADR-004.

## 1. Проблема

Новый участник должен получить room key, **когда ни один уже авторизованный участник не онлайн** и не может ответить на `key_request`. Сейчас `join_room` при `online_count==0` создаёт лишь `PendingKeyRequest` — участник не получает ничего до появления онлайн-члена (`rooms/keys.py`).

Сломанный sealed-prekey механизм (удалён в ADR-004) пытался это решить, но был **несалважим E2E**: оборачивал room key на one-time pubkey с выброшенным приватным. Урок: **нельзя обернуть ключ для участника, чей публичный ключ неизвестен на момент обёртки**, а «anonymous + claimable-by-anyone + offline + E2E» — противоречие.

## 2. Модель угроз

Как в ADR-002/004: **A1 (honest-but-curious сервер) — ЗАЩИЩАЕМ**; **Б2 (активный злонамеренный сервер) — вне скоупа**, но границы отмечаем. Сервер НИКОГДА не видит room key, escrow-секрет или приватные ключи.

## 3. Сужение скоупа (advisor)

Бо́льшая часть случаев НЕ требует новой крипты — «никто не онлайн на join» кусает только там, где не было онлайн-члена, знавшего вступающего:

| Ячейка | Есть онлайн-член, знающий pubkey вступающего? | Решение |
|---|---|---|
| Апрув-гейт (админ одобряет заявку) | Да, на approve-time | **pre-wrap** для заявителя |
| Directed-invite («пригласить юзера X») | Да, на invite-time | **pre-wrap** для X |
| Публичная комната | — | auto-escrow (уже есть, не-E2E) — не трогаем |
| **Остаток: анонимная shareable-ссылка, приватная комната, никто не онлайн** | Нет | **escrow на invite-pubkey** |

**Состояние кода (проверено):** членство — ТОЛЬКО через анонимный `invite_code` (короткий, ~40 бит, сервер видит); `join_approval` — колонка есть, но НИГДЕ не энфорсится; directed-invite и join-request — отсутствуют. Значит «дешёвого pre-wrap хука» пока нет — его строим (Трек 1).

## 4. Решения

### 4.0. Инвариант self-heal (ОБЩИЙ, load-bearing — прямой урок sealed-prekeys)

И O1 (pre-wrap), и O6 (escrow-claim) пишут `EncryptedRoomKey` для вступающего. Эта строка может быть **неверной**: злонамеренный член pre-wrap'нул мусор; обёрнуто на устаревший/чужой pubkey; устаревший escrow (обёрнут на мёртвый ключ после ротации). Тогда вступающий видит `has_key=True`, дешифровка падает — и это **ровно тот sealed-poisoning**, который удалён в ADR-004 (сломанный ключ с `has_key=True` навсегда глушил `key_request`, лечился только JOIN-миграцией).

**Правило (обязательно для O1 и O6):** *провижн-ключ, который не дешифруется, обязан самоисцеляться* — клиент детектит decrypt-провал (InvalidTag на room_key/первом сообщении) → удаляет локальную/серверную строку → падает в `key_request`/rotation. **`has_key=True` НИКОГДА не должен глушить восстановление, если ключ негоден.** Без этого оба трека воспроизводят удалённый баг. (В отличие от sealed — здесь клиент детектит провал и чистит сам, а не оставляет отравленную строку.)

**NB (self-heal — корректность, не availability):** в ЧИСТО-оффлайн случае (никто не онлайн — целевой сценарий) self-heal убирает яд и возвращает в состояние ОЖИДАНИЯ ключа, но НЕ восстанавливает доступ мгновенно — X ждёт, пока член вернётся онлайн и ответит на `key_request`. Это корректная деградация (нет вечного лок-аута, строго лучше sealed), но не «X всегда сразу получает рабочий ключ».

### 4.1. Трек 1 — pre-wrap (основной, чистый E2E)

Онлайн-член (пригласивший/одобривший) знает аккаунтный X25519(+Kyber) pubkey вступающего → оборачивает room key для него → хранит как `EncryptedRoomKey`. Вступающий забирает оффлайн через существующий key-bundle. **Переиспользует K4-крипту** (`hybridEciesEncrypt`, `resolvePeerKyberPub`, `EncryptedRoomKey`/`EciesKeyFields`, key-bundle read) — новая только обвязка invite/approve. **Не увеличивает blast-radius**: пригласивший явно выбрал дать X доступ (то же, что ответить на `key_request`, но проактивно).

**Предусловия pre-wrap (назвать явно для O2):**
- X должен быть **уже зарегистрирован** с опубликованными X25519 **+ Kyber pub + sig, доступными пригласившему**. Контакты отдают их (K4e); **проверить, что search-эндпоинт тоже** (приглашение НЕ-контакта) — конкретная зависимость O2. Пригласить незнакомца по ссылке pre-wrap не может → это и есть остаток Трека 2 (согласованно).
- Наследует мультидевайс-ограничение K5: **свежий-login** девайс X (без vault/link) не имеет аккаунтного приватного → всё равно не дешифрует. Не регрессия, но «pre-wrap решает offline-join» — НЕ безусловно.

**Оговорка объёма (честно):** Трек 1 — в основном **новая продуктовая поверхность** (directed-invite UX, workflow апрува — `join_approval` сейчас декоративен, таблица `JoinRequest`, approve-эндпоинты). «Переиспользует K4» верно для крипты, но недооценивает вес: O2/O3 — это в основном invite/approval-обвязка, а не тонкая обёртка.

### 4.2. Трек 2 — escrow на invite-pubkey (остаток, анонимные ссылки)

- **Формат ссылки:** `join/<invite_code>#<invite_priv>`. `invite_code` (сервер видит — идентифицирует комнату, гейтит членство); `invite_priv` (высокоэнтропийный, во фрагменте `#…`, сервер НИКОГДА не видит). Сервер хранит invite **публичный** ключ.
- **Обёртка (любой онлайн-член):** `ECIES(room_key, invite_pub)` → escrow-строка на сервере. **Асимметрия обязательна (advisor):** симметричный `AES(room_key, HKDF(secret))` ломается ротацией — на rekey никто не может re-wrap (секрет только в ссылке, не у члена); с invite-**pub** любой онлайн-член re-wrap'ает на ротации, не зная секрета.
- **Приём:** вступающий по ссылке → сервер подтверждает членство (сохраняя апрув-семантику) → отдаёт escrow_ct → вступающий дешифрует `invite_priv` из фрагмента. Онлайн-член на join НЕ нужен.
- **Двойной гейт:** сервер гейтит **fetch** (по членству), фрагмент гейтит **decrypt** — ни одного по отдельности не хватает. Это сохраняет `join_approval`, если его энфорсить.
- **Устаревший escrow на ротации (тот же баг под маской, advisor):** «re-wrap на ротации» — best-effort; если пропущен (член ушёл офлайн сразу после rekey, клиент не смог re-wrap) — escrow тихо оборачивает **мёртвый** ключ → вступающий получит ключ, дешифрующий ИСТОРИЮ, но падающий на ТЕКУЩИХ сообщениях (хуже «нет ключа» — выглядит успехом). Обязательно **версионировать/инвалидировать escrow на ротации**: escrow несёт key-version; вступающий с устаревшей версией трактует escrow как отсутствующий → fallback в `key_request` (см. общий self-heal §4.0). Не «re-wrap и надейся».
- **PQ:** invite = двойная X25519+ML-KEM пара, оба приватных во фрагменте; обёртка = `hybridEciesEncrypt(room_key, invite_x25519_pub, invite_kyber_pub)` — переиспользует K4.

### 4.3. Осознанный tradeoff blast-radius (advisor, честно)

Для приватной no-approval комнаты escrow **увеличивает** радиус поражения: сегодня утёкшая ссылка ещё требует, чтобы член **активно ответил** на key_request (трение, видимость — кто-то решил ответить); escrow отдаёт ключ **мгновенно и тихо, без действия члена**. Вероятно приемлемо (митигации: per-invite-токен + отзыв, ротация ключа, TTL ссылки), но это НЕ non-issue — фиксируем как сознательный компромисс, только для остаточной ячейки Трека 2.

## 5. Батчи

Каждый дормантный/реверсивный; активация — отдельным гейтом. Порядок: приём ДО отправки (как ADR-004).

**Трек 1 — pre-wrap:**
- **O1 — server pre-provision — СДЕЛАНО (дормантно; клиент не зовёт до O2).** `POST /{room_id}/provision-key` (`ProvisionKeyRequest(EciesKeyFields)+for_user_id`): вызывающий — член С ключом; хранит `EncryptedRoomKey` для X (гибрид/классика, `eph_pub`/`kyber_ciphertext`) + добавляет X участником (`is_full`/бан-чек); **skip-if-exists** (не перетирает рабочий ключ X); доставка по WS если онлайн + `added_to_room` notify. **Self-heal (§4.0):** `DELETE /{room_id}/my-key` — участник удаляет свой негодный ключ + пере-запрос через `key_request` (без этого сломанный ключ с has_key=True навсегда глушил бы восстановление — тот же лок-аут, что sealed-prekeys). **Попутный фикс:** `PendingKeyRequest.is_expired` падал на naive-datetime из SQLite (предсуществующий баг, гейтящий именно pending-request путь offline-раздачи) → tz-робастно. Тесты `test_provision_key.py`: гибрид/классика store→fetch оффлайн, skip-if-exists, auth (не-член → 403, член-без-ключа → 403, забаненный target → 403), self-heal (DELETE → has_key=False), **live-верификация is_expired** (keyless → key-bundle дважды → нет 500). **Auth-ДОЛГ (advisor, load-bearing):** `provision-key` — ЖИВОЙ эндпоинт с **member-level** авторизацией (не `can_invite`, не апрув): любой член с ключом может добавить произвольного user_id и провижнить ключ БЕЗ согласия target. Не confidentiality-дыра (добавляющий и так имеет доступ) + дормантно-по-UI, но: (1) обходит будущий `join_approval`; (2) griefing — злонамеренный член гонкой провижнит мусор первым, skip-if-exists блокирует хороший провижн, target застрял до self-heal. **O3 ОБЯЗАН согласовать `provision-key` с апрувом** (гейт на `can_invite`/роль + pending при `join_approval`), иначе апрув тривиально обходится любым членом.
- **O2 — РАЗДЕЛЁН (advisor): O2a send (флаг-гейт/дормантно) + O2b self-heal (LIVE/always-on).** Причина: self-heal — receive-side, не флагуется (реагирует на decrypt-провалы независимо от send-флага); мешать дормантно-реверсивную и живо-деструктивную половины в одном батче = неверная категоризация (трек всегда делил receive/send: K4b/K4c).
  - **O2a — client directed-invite — СДЕЛАНО (за флагом `vortex_offline_invite_enabled`, дефолт ВЫКЛ).** Сервер: kyber_public_key+sig в user-search (`search.py`) — зависимость pre-wrap НЕ-контакта (как contacts K4e). Клиент `provisionRoomKeyForUser(roomId, targetUserId, targetPubkeys)` (`rooms/core.js`): `getRoomKey` (иначе skip) → `resolvePeerKyberPub` (verified Kyber; fetch-and-pin для незнакомца — та же TOFU-модель) → `hybridEciesEncrypt` (kyber=null → классика) → `POST /provision-key`. **Two-flag coupling (advisor, rollout-факт):** directed-invite ГИБРИДЕН только когда включён И `vortex_offline_invite_enabled`, И `vortex_pq_hybrid_enabled` (`resolvePeerKyberPub` гейтится на `pqSendEnabled()`); при одном offline-флаге pre-provision КЛАССИЧЕСКИЙ (безопасно, но без PQ). Тесты: `test_search.py` (search несёт kyber-sig); браузер-гейт `offline-invite.spec.js` (оба-выкл→skip; offline-only→**классический** POST; оба флага+capable→**гибридный** POST; перехват тела, обе ветки). Glue покрыт транзитивно (pq-capability/crypto-hybrid/provision-key); stranger fetch-and-pin — в `pq-capability.test.js`. UX-кнопка — тонкий follow-up (функция на `window`).
  - **O2b — self-heal receive-детекция — СДЕЛАНО (LIVE/always-on, не за флагом).** Хелпер `selfHealRoomKey(roomId, error, privKeyPresent)` + `markRoomKeyHealthy(roomId)` (`chat/room-crypto.js`). Провязан во ВСЕ 3 сайта приёма room-key: `websocket.js` (`case 'room_key'` + `_pullKeyFromServer` — decrypt изолирован от сетевого catch), `notifications.js` (`_handleRoomKeyFromNotif`). На decrypt-провале → `DELETE /{roomId}/my-key` (O1, удаляет СЕРВЕРНУЮ строку — локальная-only зациклит) + сервер шлёт key_request. На успехе → `markRoomKeyHealthy` (сброс счётчика). **Три гейта advisor выполнены:** (1) **правило детекции** — хилим ЛЮБОЙ провал КРОМЕ `Error('...requires local Kyber identity')` (нет Kyber-priv → re-request даст такой же гибрид, нехилимо/K5-лимит); (2) **bounded-not-spinning** — `HEAL_MAX=2` на комнату, потом `'unrecoverable'` → user-visible `keyDecryptErrorFull`, НИКОГДА не крутит; (3) **false-positive** — `privKeyPresent` guard в проде **инертен** (advisor): все 3 сайта early-return при `!privKey` ДО хелпера → `privKeyPresent` всегда true; лёгкую половину (priv не загружен) закрывают эти early-return выше, а ЖЁСТКУЮ (priv загружен, но ЧУЖОЙ — мультиаккаунт/stale) держат ТОЛЬКО bounded + серверный роутинг (room_key идёт на аккаунт-член) + recoverable, НЕ priv-guard. UI: healing→`keyUpdated`, unrecoverable→`keyDecryptErrorFull` (в т.ч. на pull-пути — молчание исправлено), skip→`keyDecryptErrorDetail`.
    - **Риск амплификации (advisor, принят):** self-heal always-on/деструктивен — СИСТЕМНЫЙ decrypt-баг (формат/релей/деплой; трек уже возил такие: is_expired-500, envelope-mismatch) раньше оставлял ключи целыми (пофиксил баг → decrypt возобновился), теперь заставит каждый затронутый клиент УДАЛИТЬ серверный ключ (bounded на комнату, но каждую комнату раз) → «decrypt сломан, recoverable» → «ключи снесены, надо re-request», для DM с оффлайн-пиром — застревание до его возврата. Правило детекции нарочно широкое (максимум ловли яда) — оно же максимизирует амплификацию. Защита оправдана: `provide-key`/`handle_key_response` ПЕРЕЗАПИСЫВАЮТ ключ (в отличие от O1 skip-if-exists) — реальный вектор отравления. Принято с ценой восстановления.
    - **Тесты:** `room-key-heal.test.js` (5 — Kyber-skip, priv-guard, healing+DELETE, bounded→unrecoverable, reset); браузер-гейт `room-key-heal.spec.js` — A: правило детекции на РЕАЛЬНЫХ ошибках движка (неверный Kyber→AEAD→heal, нет Kyber→skip; DELETE только на heal; bounded); **B: реальный e2e** — отравленный ключ через настоящий `_pullKeyFromServer` → DELETE с правильным roomId (не inspection-only wiring; тот же glue-gap, что скрыл 3 stories-бага). Защищает СЕЙЧАС: O1/provide-key live-callable — злонамеренный член может отравить target.
- **O3 — approval flow + согласование auth O1 — СДЕЛАНО (дормантно за Config.JOIN_APPROVAL_ENFORCED=OFF).** **Флаг-стратегия (решение оператора):** глобальный серверный Config-флаг поверх per-room `join_approval` — существующие `join_approval=True` комнаты СОХРАНЯЮТ поведение до осознанного флипа (иначе энфорс мгновенно загейтил бы их на деплое; per-room флаг сам по себе — не дормантность). `_approval_enforced(room)` = per-room флаг И Config-флаг. **Модель** `JoinRequest` (`room_join_requests`, uniq room+user) — pending-заявка НЕ RoomMember (важно: `_require_member` 403'ит заявителя ВЕЗДЕ — safe by construction, отдельная таблица, не `RoomRole.PENDING`). **Единый предикат `_can_admit(actor, room)`** (helpers) = ADMIN/OWNER всегда, иначе только если апрув не энфорсится — вызывается И `provision-key`, И `approve-join` (без дрейфа, advisor). `join_room`: при энфорсе → `JoinRequest` (dedup), возвращает `{pending:true}`, НЕ добавляет членом. Эндпоинты: `GET /{id}/join-requests` (админ, несёт kyber-pub+sig для pre-wrap), `POST /{id}/approve-join` (админ: добавляет член + опц. pre-wrap ключа skip-if-exists + удаляет заявку), `POST /{id}/reject-join`. **provision-key реконсиляция:** при добавлении нового члена → `_can_admit` (обычный член не обойдёт апрув). Тесты `test_join_approval.py` (6): энфорс→pending-не-член, **LOAD-BEARING негатив-реконсиляция** (член с ключом провижнит незнакомца на approval-комнате → 403, не член), admin approve→член+ключ+заявка-удалена, reject, join_channel-гейт, дормантность (Config OFF → join добавляет сразу).
    - **RoomMember-creation sweep (advisor, дисциплина трека):** прогрет `grep 'db.add(RoomMember('`. Загейчены user-facing JOIN-пути: `join_room` (rooms/keys.py), `join_channel` (channels.py — каналы это Room с join_approval). **Осознанно out-of-scope (не джойн-по-апруву):** channels.py:547 (paid-subscription — подписка есть решение о допуске), spaces.py `_add_user_to_room`/space-room-create (space-membership — инстанция допуска; per-room апрув внутри space — отдельный концерн), боты (bot_marketplace/bot_crud/antispam — install/config-флоу), DM (is_dm, без апрува), create/owner-пути (crud/channels/spaces создание — владелец). `provision-key`/`approve-join` — через `_can_admit`.
    - **Dangling JoinRequest (advisor):** если админ впускает заявителя через `provision-key` (не approve-join), его pending-заявка чистится в add-member ветке (иначе висела бы в списке).
    - **Alembic-caveat:** `JoinRequest`-таблица создаётся `create_all` на SQLite/no-Alembic пути (допущение всего трека — как PQ-колонки в SQLite-only ветке миграций); при Postgres/Alembic-проде нужна отдельная миграция (тот же K5-caveat).

**Трек 2 — escrow (остаток):**
- **O4 — invite-link формат + escrow-схема — СДЕЛАНО, затем АМЕНДЖЕНО O5a (single-table → two-table).** ⚠️ Изначальная single-table `RoomInviteEscrow` (identity+обёртка вместе) НЕ поддерживала «any member re-wrap» — delete-on-rotation удалял и `invite_pub` → re-wrap невозможен. O5a разделил: `RoomInvite` (identity, персистит) + `RoomInviteEscrow` (только обёртка, удаляется на ротации). Ниже — исходный O4-текст; актуальная схема — в O5a. Модель `RoomInviteEscrow` (`room_invite_escrows`, uniq room+invite_pub): обёртка room key на invite-pub (EciesKeyFields-форма, гибрид/классика) + `invite_pub`/`invite_kyber_pub`; `to_client_dict()`. **Решения (advisor-blessed):** (1) идентификатор escrow — сам `invite_pub` (joiner выводит из фрагмент-priv, запрашивает по нему; отдельный токен не нужен; per-invite → revoke=удалить); (2) устаревание — **delete-on-rotation** (проще version-сравнения, переиспользует key_request-fallback: отсутствующий escrow → key_request). Эндпоинты (keys.py): `POST /invite-escrow` (член с ключом, upsert), `GET /invite-escrow?invite_pub=` (**double-gate: `_require_member` — ЧЛЕНСТВО, не владение ссылкой; фрагмент-priv гейтит decrypt**), `DELETE` (revoke). **Rotation-sweep (advisor, дисциплина трека — широкий греп):** `_invalidate_room_escrows` во ВСЕХ 3 сайтах ротации (все, кто меняет значение room key + шлёт key_rotated): `rotate_room_key`, `kick`, `leave`. Прочие delete-EncryptedRoomKey адъюдицированы: `forget_my_key`/panic-per-user/crud-read — фильтр `user_id==` (значение ключа не меняется → escrow не трогаем); panic DM-wipe — `db.delete(room)` → escrow CASCADE. Ни один сайт ротации не пропущен. **Revoke-auth (осознанно any-member):** `revoke` гейтится `_require_member` (не `_can_admit`) — симметрично store (любой член с ключом создаёт/отзывает); griefing безопасен (offline-join → key_request-fallback, без экспозиции ключа); ужесточить до admin/inviter — опция O7. **Честно (advisor):** «dormant data-plane, live control-plane» — эндпоинты дормантны (клиент не зовёт до O5/O6), но rotation-invalidation LIVE сразу (no-op пока escrow'ов нет). **Отложенный feature-gap (назван, не решён):** delete-on-rotation → offline-join работает ТОЛЬКО до следующей ротации; post-rotation offline-join требует онлайн-члена для re-wrap (O5) — присуще дизайну (нельзя re-wrap без room key). **Alembic-caveat (3 новых таблицы):** `room_join_requests` (O3), `room_invite_escrows` (O4), `room_invites` (O5a) создаются `create_all` на SQLite/no-Alembic пути; при Postgres/Alembic-проде нужна миграция для ВСЕХ ТРЁХ (иначе `/invites`/store/re-wrap → 500; тот же K5-caveat). Тесты `test_invite_escrow.py` (9): store→fetch гибрид/классика, **LOAD-BEARING** (fetch не-члена → 403, pending-заявитель O3 → 403 = double-gate сохраняет апрув), store-требует-ключ, revoke, **sweep** (rotate/kick/leave инвалидируют).
- **O5 — РАЗДЕЛЁН (advisor): O5a two-table рефактор + серверная re-wrap-основа + O5b клиент wrap/re-wrap/UX.**
  - **O5a — two-table рефактор — СДЕЛАНО (амендит O4; серверно, дормантно).** Причина: «any online member re-wrap на ротации» (§4.2) требует `invite_pub` пережить room key — но O4 delete-on-rotation его удалял. **Split:** `RoomInvite {room_id, invite_pub, invite_kyber_pub, created_at}` (ПЕРСИСТИТ через ротацию — identity + PQ-pub, чтобы re-wrap не ронял гибрид) + `RoomInviteEscrow {invite_pub → ephemeral_pub, ciphertext, kyber_ciphertext}` (обёртка, удаляется на ротации). `store /invite-escrow` upsert'ит ОБЕ (identity + обёртку); `GET /invites` (membership-gated) отдаёт `invite_pub`+`invite_kyber_pub` для re-wrap; `revoke` удаляет ОБЕ (иначе ротация оживила бы утёкшую ссылку). `_invalidate_room_escrows` (rotate/kick/leave) удаляет ТОЛЬКО `RoomInviteEscrow` — `RoomInvite` жив. **Решения (advisor):** invite_kyber_pub персистит (иначе ротация тихо роняет PQ→классику); re-wrap делает ОДИН writer (ротация-триггерящий клиент, не «каждый, кто видит key_rotated» — upsert идемпотентен, но без стампеда). **Blast-radius (принято, advisor):** персистентный `RoomInvite` = стоячий key-access-грант — утёкшая ссылка **ре-армится на каждой ротации** пока не отозвана (усиливает нужду в real revoke + TTL O7). Fetch/`_require_member` double-gate не тронут. Тесты `test_invite_escrow.py` (11): + личность в /invites, revoke удаляет обе, **ротация удаляет обёртку но identity+Kyber-pub персистят** (load-bearing two-table), re-wrap upsert.
  - **O5b — client wrap + re-wrap — СДЕЛАНО (за флагом `vortex_offline_invite_enabled`, дефолт ВЫКЛ).** Модуль `dr/invite-link.js`: `createInviteLink(roomId, inviteCode)` — генерит invite-пару (X25519 `generateKey` + ML-KEM `mlkemKeygen`), `hybridEciesEncrypt(roomKey, invitePub, kyberPub)` → `POST /invite-escrow` (+invite_pub/invite_kyber_pub), возвращает ссылку `join/<invite_code>#<b64url({x:X25519-priv-JWK, k:ML-KEM-priv-hex})>` (приватные ТОЛЬКО во фрагменте, сервер не видит). `rewrapInvitesAfterRotation(roomId, newKey)` — `GET /invites` → на каждый `hybridEciesEncrypt(newKey, invite_pub, invite_kyber_pub)` → `POST` (идемпотентно, upsert). **Хук re-wrap** в `websocket.js` `case 'key_rotated'` после `setRoomKey` (dynamic import, флаг-гейт внутри → no-op без флага/invite'ов). **Re-wrap best-effort (advisor, честно):** key_rotated-хендлер генерит новый ключ на КАЖДОМ клиенте с открытой комнатой (пре-существующая multi-generator логика — ротация НЕ гарантированно сходится на один ключ) → каждый такой клиент re-wrap'ает escrow на СВОЙ newKey, last-writer выигрывает строку. Winner может быть НЕ тем ключом, на который сойдётся комната → вступающий получит escrow с ключом, которого ни у кого нет → расшифрует мусор → **fallback в key_request (safe, ловит self-heal O2b)**. Т.е. escrow-после-ротации — **best-effort, key_request-backed**, а не «условно-корректен»; фикс самой rotation-race — вне scope O5 (пре-существующий). Функции на `window` (UX-кнопка «создать ссылку» — тонкий follow-up). Тесты: `invite-link.test.js` (5 — флаг/нет-ключа → null, createInviteLink гибрид-POST+ссылка+фрагмент {x,k}, rewrap GET+POST, флаг-выкл→без api); браузер-гейт `invite-link.spec.js` (**round-trip: wrap на invite-pub → decrypt приватными ИЗ ФРАГМЕНТА = исходный room key** — O5b→O6 seam; + re-wrap POST на persisted invite).
- **O6 — вступающий дешифрует escrow — СДЕЛАНО (за флагом `vortex_offline_invite_enabled`).** `redeemInviteEscrow(roomId, fragment)` (`dr/invite-link.js`): парсит фрагмент `b64url({x:X25519-JWK, k:ML-KEM-hex})`, выводит `invite_pub` из JWK-поля `.x` (публичный), `GET /invite-escrow?invite_pub=` (**membership-gated на сервере — вступающий уже член**), `hybridEciesDecrypt(escrow, x, k)` → `setRoomKey`. **Fallback:** нет ключа для комнаты не выполнен / нет фрагмента / has_escrow=false (устаревший после ротации) / decrypt-провал (best-effort O5b) → `null` → обычный `key_request`-путь (self-heal §4.0). **Хук** в `websocket.js _pullKeyFromServer`: при key-bundle `has_key=False` + есть `location.hash` → `redeemInviteEscrow` ДО ожидания key_request; успех → **`history.replaceState` стирает фрагмент** (иначе приватные {x,k} висят в URL/истории + ре-триггерят redeem на каждом open) + `setRoomKey`+флаш истории (извлечён общий `_flushPendingHistory`). Функция на `window`. **invite_pub-деривация (advisor, load-bearing raw-vs-JWK footgun):** тест ловит GET-query `invite_pub` и сверяет с raw-export'ом store'а — доказывает, что `_invitePubFromJwk(.x)` (redeem) == `toHex(exportKey('raw', pub))` (store), иначе GET нашёл бы 0 строк → вступающий ждал бы отсутствующего члена. Тесты `invite-link.test.js` (8, +3 O6): фрагмент+escrow→расшифровка+setRoomKey (+ **invite_pub==raw-export**), has_escrow=false→null, флаг-выкл/нет-фрагмента/есть-ключ→null; браузер-гейт `invite-link.spec.js` — **full round-trip через РЕАЛЬНЫЙ redeemInviteEscrow** (createInviteLink→escrow→redeem по фрагменту→исходный room key) + re-wrap.
- **O7 — активация — КОД-ПРЕДУСЛОВИЯ СДЕЛАНЫ; флип+гейт-ран — за оператором (как K5).**
  - **РЕШЕНИЕ (оператор): invite-creation = «любой член с ключом»** (не admit-gated) — согласовано с открытой invite_code-моделью (любой член шарит код). Blast-radius митигируется TTL + any-member revoke, НЕ ограничением круга создателей.

Энфорс read-time во ВСЕХ invite-read/act путях (свип, дисциплина трека): `GET /invite-escrow` (истёкший → `has_escrow=false`), `GET /invites` (**исключает истёкшие** — иначе re-wrap ре-армит истёкшие вечно → TTL декоративен), клиентский re-wrap наследует (через /invites). tz-робастный `_invite_expired` (naive из SQLite). Свип RoomInvite read/act: store/list/get покрыты, revoke удаляет независимо.
  - **Revoke — any-member (advisor, осознанная асимметрия):** создавать контролируемо (любой член), отзывать легко (любой член) — быстрый kill утёкшей ссылки лучше «tidy authority». Не тронут.
  - **Alembic-caveat:** `expires_at` на `room_invites` — ALTER в SQLite-only ветке (как весь трек; Postgres/Alembic → отдельная миграция). Cleanup истёкших строк — housekeeping-follow-up (безопасность на read-time энфорсе, не на удалении).
  - **TTL-exempt residual (advisor, honesty):** `expires_at` nullable, NULL = не истекает → инвайт, созданный в окне O5a→O7 (без колонки, ALTER даёт NULL), TTL-освобождён навсегда. **Vacuous при атомарном релизе** (весь трек O1–O7 одним деплоем, unreleased/flag-off — таких инвайтов нет). Тот же класс, что K5 old-bundle-residual.
  - **Не флип (как K5):** O7 = митигации в коде + существующие гейты зелёные на реальном движке (оператор запускает `pq-hybrid`/`invite-link`/`room-key-heal` spec'и) + флип-процедура. **Флип-процедура (оператор):** (1) деплой; (2) зелёные браузер-гейты (≥ Chrome+Firefox); (3) флип `vortex_offline_invite_enabled='1'` (per-client) — приём/redeem всегда-читают escrow, но создание/re-wrap за флагом; (4) при утечке ссылки — revoke + ротация room key.
