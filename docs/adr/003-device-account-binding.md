# ADR-003: Асимметричный device→account binding (P1 для Sesame)

- **Статус:** Accepted. Feasibility закрыт (go). P1-реализация: устройство публикует ПУБЛИЧНЫЕ части тройки (device X3DH pub, device signing pub, account cert над ними) в prekey-бандле; cert верифицируем отправителем против аккаунтного `identity_key_ed`. Сервер cert НЕ проверяет. Проверка cert'а и переключение подписи SPK на device signing-ключ — на **fan-out (M3)**; approver-signing нового устройства при линковке — **M4**. Bootstrap первого устройства — self-sign (MVP).
- **Дата:** 2026-07-12
- **Связано:** [ADR-002](002-multi-device-v2-sesame.md) §2a (P1 — блокирующее предусловие Sesame), [ADR-001](001-message-encryption-versions.md) §2.4г (TOFU идентичности)
- **Тип:** только дизайн, кода нет. Отвечает на вопрос: **жизнеспособен ли вариант (a)** и **какой формы должна быть device-identity** (это определяет P2).

## 1. Что должен решить P1

Отправитель **Alice** (другой пользователь) шлёт v2-сообщение **Bob**, у которого несколько устройств. Alice получает список device-бандлов Bob и обязана решить, **какие устройства реально авторизованы аккаунтом Bob**, — иначе злонамеренный сервер вставит фиктивное устройство в fan-out-набор и прочитает всё (ADR-002 §4). Требования к binding:

- **Асимметричный** — проверяемый Alice, которая не держит ни одного секрета Bob. (Поэтому `DeviceCrossSign` с HMAC не годится: HMAC проверяет только держатель ключа.)
- **Укоренён в «аккаунте Bob»** — в аккаунтной Ed25519-идентичности Bob (`identity_key_ed`, ADR-001 батч 4), которую Alice (со временем) верифицирует внеполосно (safety-number).

## 2. Почему существующие примитивы

| Примитив | Есть? | Роль в P1 |
|---|---|---|
| Аккаунтный Ed25519 identity (`identity_key_ed`) | да (батч 4) | **корень доверия**: подписывает авторизацию устройств |
| Device X25519 keypair (`device_pub_key` + `vortex_device_priv_jwk`) | да | X3DH-идентичность устройства |
| `DeviceLinkRequest` (link_code → одобрение → ECIES-перенос ключей) | да | **точка переноса доверия**: одобряющее устройство видит pub нового и переносит ключи |
| `key_transparency_log` | да | аудит набора устройств (анти-подмена/сокрытие сервером) |
| Per-device **Ed25519 signing key** | **нет (новое)** | устройство подписывает свои SPK, не трогая аккаунтный ключ на ротации |
| `DeviceCrossSign` (HMAC) | да, но **не подходит** | симметричный — внешний отправитель не проверит |

Единственный новый примитив — per-device Ed25519 signing key. Всё остальное уже в Vortex.

## 3. Схема

### 3.1. Ключи устройства (то, что P2 обязана стабилизировать)

Каждое устройство держит **три** долговременных объекта (все переживают logout, стабильны):

1. **Device X3DH key** — X25519. DH в X3DH. **Уточнение при реализации:** это **отдельный per-account** ключ из тройки (`vortex_device_identity_<userId>`), а НЕ device-global `UserDevice.device_pub_key` (`vortex_device_pub`). Per-account выбран ради приватности: общий на устройстве `device_pub_key` линковал бы аккаунты одного физического устройства для сервера. `device_pub_key` остаётся для device-management (fingerprint, cross-sign) — это другая забота. Публикуется как `device_x3dh_pub` в prekey-бандле.
2. **Device signing key** — Ed25519 (новое, per-device). Подписывает SPK этого устройства.
3. **Authorization certificate** — подпись аккаунтного Ed25519 над `(device_id ‖ device_x3dh_pub ‖ device_sign_pub)`. Связывает устройство с аккаунтом.

> Вывод для P2: device-identity — это НЕ просто X25519-ключ, а **тройка {X25519 X3DH, Ed25519 signing, account-signed cert}**. P2 обязана стабилизировать/персистить все три + cert, а не только X25519. Именно поэтому P1 шёл раньше P2.

### 3.2. Цепочка доверия (что проверяет Alice)

```
аккаунтный Ed25519 (Bob)  ──sign──▶  device authorization cert  ──▶  device signing key (Ed25519)  ──sign──▶  device SPK
        ▲ верифицируется Alice внеполосно (safety-number)
```

Alice для каждого device-бандла Bob проверяет:
1. `Ed25519_verify(bob_account_ed_pub, device_id‖x3dh_pub‖sign_pub, cert_sig)` — аккаунт Bob авторизовал это устройство.
2. `Ed25519_verify(device_sign_pub, spk, spk_sig)` — SPK подписан ключом этого устройства.
3. `bob_account_ed_pub` — тот, что Alice верифицировала внеполосно.

Устройство без валидного cert (в т.ч. вставленное сервером) в fan-out-набор **не включается** — сервер не может подделать подпись аккаунтного Ed25519 Bob.

**Разделение обязанностей signing key vs account key:** аккаунтный Ed25519 подписывает device-cert **один раз** (при авторизации устройства). SPK ротируется часто — их подписывает **device signing key**, не требуя аккаунтного ключа. Значит устройство ротирует prekeys свободно, а аккаунтный ключ не нужен на устройстве после авторизации.

### 3.3. Флоу авторизации устройства (кто и когда подписывает)

- **Первое устройство** (создатель аккаунта): держит аккаунтный Ed25519 с регистрации → **само-подписывает** свой cert.
- **Новое устройство (через `DeviceLinkRequest`):** одобряющее устройство держит аккаунтный Ed25519. По существующему флоу оно **видит X25519-pub нового устройства** (шаг 2) — расширяем: новое устройство передаёт и свой `device_sign_pub`; одобряющее **подписывает cert нового устройства** аккаунтным Ed25519 и загружает его. Новое устройство получает cert (публичный) — **аккаунтный Ed25519-приватный ему передавать НЕ обязательно**.

**Ключевое решение — blast radius.** Аккаунтный Ed25519-приватный остаётся **только на устройствах-авторизаторах** (первое + явно повышенные), а не расходится на каждое линкованное устройство. Новое устройство получает лишь свой cert. Это уже, чем нынешний `DeviceLinkRequest`, который ECIES-переносит `encrypted_keys` (включая, вероятно, аккаунтные ключи) — при реализации перенос аккаунтного Ed25519 на обычные устройства следует **исключить** (переносить аккаунтный X25519 для v0/v1 roomKey-ECIES — да; аккаунтный Ed25519 — нет). Разрешает и опасение ADR-002 §4 «аккаунтный Ed25519 достижим только через vault-restore»: новому устройству он не нужен.

**Реализовано (M4b, ADR-002 §3 M4).** Одобряющее подписывает cert нового устройства аккаунтным Ed25519 и передаёт **аккаунт-материал `{device_cert_sig, account_ed_pub, identity_key_sig}`** — три аккаунт-уровневых ПУБЛИЧНЫХ константы. Линкуемое устройство публикует полный prekey-бандл БЕЗ аккаунтного Ed25519-приватного (перенос `ed25519_identity_jwk` при линковке убран; при vault-backup остаётся — self-restore). **`identity_key_sig` НЕ делать опциональным** на приёме: это binding account-X25519↔account-Ed, который проверяет sender-гейт `_bundleWellSigned`; ослабление затронуло бы ВСЕ устройства, не только линкованные — линкуемому передаётся ЗНАЧЕНИЕ (константа), а не приватный.

### 3.4. Отзыв и key-transparency

- **Отзыв устройства — принуждаем только с настоящей KT-системой (см. §4(2)).** Подписанная аккаунтным Ed25519 запись отзыва необходима, но **недостаточна**: сервер её просто опускает и реплеит до-отзывное состояние. Чтобы отзыв работал против злонамеренного сервера, нужна non-equivocation — gossip между наблюдателями или сторонний аудитор (CONIKS/Keybase-стиль). `key_transparency_log` как таблица этого не даёт. Это отдельная крупная зависимость (см. §5).
- **Аудит другими устройствами Bob** ловит инъекцию/сокрытие **только если** устройства Bob и Alice видят один и тот же лог (та же non-equivocation). Единственный сервер раздаёт разные виды разным наблюдателям — без gossip/аудитора аудит обходится.

## 4. Остаточное доверие — РАЗНОЕ для добавления и отзыва

Нельзя сводить всё к «то же TOFU, что у single-device». Активно-злонамеренный сервер атакует набор устройств **двумя зеркальными способами**, и они решаются по-разному:

**(1) Добавление — инъекция поддельного устройства. РЕШЕНО, сводится к account-key TOFU.** Поддельному устройству нужна валидная подпись аккаунтного Ed25519 Bob → без приватного ключа Bob невозможно, даже серверу. Alice проверяет cert. Остаток — доверие к самому аккаунтному Ed25519 (safety-number) — **то же ограничение, что у single-device** (ADR-001 §2.4г). Здесь «не хуже single-device» верно.

**(2) Отзыв — прекратить шифровать украденному/выведенному устройству. Зависит от модели угроз:**

- **Под A1 (honest-but-curious сервер — основная защищаемая моделью Vortex):** отзыв **работает**. Подписанную аккаунтным Ed25519 запись отзыва честный сервер исполняет, перестаёт отдавать устройство в наборе, Alice перестаёт ему шифровать. В модели, которую v2 реально таргетит, отзыв в порядке.
- **Под Б2 (активно-злонамеренный сервер):** отзыв ломается через suppression/replay — сервер опускает запись отзыва и реплеит до-отзывное состояние (устройство ещё в списке, cert ещё валиден); Alice не отличит «не отозвано» от «скрыто». Safety-number по ключу тут бессилен (подделан не ключ, а устаревший-но-подлинный вид). Для принуждения нужна non-equivocation (gossip/сторонний аудитор, CONIKS/Keybase-стиль); таблица `key_transparency_log` этого не даёт.

**Но Б2 уже вне скоупа проекта** (ADR-001 §2.3): активно-злонамеренный сервер не защищается **нигде**. И v1 имеет **тот же** разрыв: `rotate-key` раздаёт новый room_key через member-set, отдаваемый сервером, — враждебный сервер равивокирует на составе так же. То есть провал отзыва под Б2 — **не v2-специфичный регресс**, а пре-существующая граница активного сервера.

**Единственный v2-специфичный остаток (реальный):** под Б2 cert делает инъекцию устройства **криптографически невозможной** (сервер не подделает подпись аккаунта — это ЛУЧШЕ, чем у v1), но suppression делает отзыв непринуждаемым. Асимметрия «**добавить устройство безопасно можно, убрать — нет**» — честная новая деталь мультидевайса, но живёт она внутри уже-вне-скоупа Б2, а не в защищаемой A1.

**Граница линковки под Б2 (M4b, принятое ограничение того же тира).** Cert выдаётся одобряющим по тройке нового устройства, которую сервер РЕЛЕИТ (тройка идёт через `/link/{code}`, 6-значный код — внеполосный аутентификатор запроса, но НЕ commitment ключей — 20 бит, сервер сгриндит подмену за ~2²⁰). Под Б2 сервер подменяет тройку → одобряющий подписывает cert на ключи сервера → импперсонация. НО: (1) это **строгое улучшение** над до-M4b, где сервер подменял `new_device_pub` и получал ВЕСЬ бандл ВКЛ аккаунтный Ed25519-**приватный** (полный захват аккаунта) — теперь получает лишь device-cert (ограниченная импперсонация сообщений, корень на месте); (2) под A1 (скоуп) честный сервер релеит верно; (3) Б2-принуждение потребовало бы ~128-битного кода (QR) — UX вне скоупа. Safety-number по аккаунтному ключу — ортогональный Б2-детектор подмены. Та же граница активного сервера, что у отзыва и v1-`rotate-key`, не v2-специфичный регресс.

## 5. Вердикт жизнеспособности (go/no-go)

**Вариант (a) ЖИЗНЕСПОСОБЕН в защищаемой моделью Vortex угрозе (A1).**

- **Механизм binding строится** на существующих примитивах (аккаунтный Ed25519, device X25519, `DeviceLinkRequest`) + один новый (per-device Ed25519 signing key). Опасение ADR-002 §4 (аккаунтный Ed25519 недостижим на линкованном устройстве) **снято** (подписывает одобряющий).
- **Под A1 (honest-but-curious — основная модель):** и инъекция, и отзыв устройств **работают**. Мультидевайс v2 в защищаемой модели полноценен.
- **Под Б2 (активный сервер) — вне скоупа проекта, как и всё Б2:** инъекция **криптографически невозможна** (лучше v1), отзыв не принуждаем (как v1-`rotate-key`). Не v2-специфичный регресс — та же граница активного сервера (§4.2).

**Что это меняет для трека:**
- **P2 переопределена.** Device-identity = тройка {X25519 X3DH, Ed25519 signing, account-signed cert} + стабильный `client_device_id`. P2 стабилизирует всё это (а не только X25519). Ради этого P1 шёл первым.
- **Уточнённый порядок:** P1(готов) → **P2** → M1 → M2 → M3 (fan-out; проверка cert'ов) → M4 (жизненный цикл).
- **Стоимость (a):** P1 + P2(расширена) + M1–M4 + **safety-number по аккаунтному ключу** (ортогонально; нужен и single-device; покрывает инъекцию). Настоящая **key-transparency с non-equivocation** — **опциональное усиление за пределами текущей границы угроз Б2**, а НЕ обязательная зависимость (v1 живёт без неё). Нужна, только если проект решит защищать отзыв устройств против активного сервера — чего он сегодня не делает ни для чего.
- **Развилка (a)/(c) с честным ценником:** (a) технически возможен и в A1 полноценен (инъекция+отзыв работают). Единственный новый мультидевайс-специфичный факт — под Б2 асимметрия «добавить безопасно / убрать нельзя», но Б2 уже вне скоупа. Вопрос продукту чисто в стоимости (P1+P2+M1–M4 + safety-number), а НЕ в дыре безопасности внутри защищаемой модели.

## 6. Открытые крусы и под-вопросы

**За пределами текущей границы угроз (опционально, НЕ блокирует (a) в модели A1):**

0. **Принуждаемый отзыв устройств против активного сервера (Б2) = настоящая key-transparency** (non-equivocation: gossip/сторонний аудитор). Под A1 отзыв уже работает; под Б2 — нет, но Б2 вне скоупа проекта, и v1 имеет тот же разрыв (§4.2). Строить только если проект расширит границу угроз до активного сервера — тогда единым треком для v1 и v2.

**Предусловие, вскрытое при P2 — стабильность аккаунтного Ed25519 (корня binding-цепочки):**

0-bis. **Аккаунтная идентичность не переживает обычный logout→login (ОБА ключа) — корень binding-цепочки нестабилен.** Проверено по коду (не по предположению):
  - `vortex_ed25519_identity_<uid>` **и** `vortex_x25519_priv_enc` **оба** чистятся при logout (auth.js:999, :1010). Сервер приватные ключи не хранит (E2E), seed их не деривирует, `_autoSyncKeys`/vault-restore — passphrase-gated/manual, на обычном логине НЕ срабатывают (`_restoreKeyBundle` зовётся только из явного модала / device-link / device-sync с уже загруженным ключом). То есть **автоматического восстановления на рутинном логине нет ни для одного ключа.**
  - **Асимметрия сбоя:** X25519 `loadPrivateKey` при отсутствии возвращает **null** → приложение падает ВИДИМО («зашифровано, нет ключа», пользователь замечает). Ed25519 `loadOrCreateEd25519Identity` при отсутствии **генерирует** → падает ТИХО: минтит новую валидную-с-виду идентичность, republish под ней, и (когда Sesame поедет) все пиры, верифицировавшие старую, тихо теряют доверие. Форк хуже, чем null.
  - **Первичная «зеркалим X25519 `_enc`» была ложной:** у X25519 `_enc` тоже в wipe-списке — зеркалить нечего. Латентный замысел `_enc` («зашифрованная-at-rest, разблокируемая паролем идентичность, переживающая logout») сломан тем, что `_enc` попал в wipe.
  - **Когерентный фикс — C для ОБОИХ ключей:** убрать `_enc`-копию из wipe-списка (плейнтекст по-прежнему чистится — shared-device гигиена сохранена: at-rest без пароля нечитаемо), восстанавливать на логине по паролю, добавить обработку session-restore-без-пароля. Плюс убрать форк-семантику Ed25519 (генерировать только при регистрации, иначе — как X25519, отсутствовать видимо).
  - **Это auth-layer изменение (оба ключа, wipe-список, login-restore, session-restore gap), не Sesame-internal** — с собственным blast radius в разделяемом auth-коде. P2 смягчает лишь ЛОКАЛЬНО (cert self-heal при смене подписанта), но churn корня остаётся. Требует продуктового/скоуп-решения перед M1 (см. вынос ниже).

**Под-вопросы реализации (не feasibility):**

1. **Bootstrap-доверие первого устройства** — self-sign (TOFU на первое устройство); совпадает с общим TOFU §4.1.
2. **Формат каноникализации** cert'а (порядок/кодировка полей) — зафиксировать для кросс-проверки.
3. **Перенос ключей при линковке** — что ECIES-переносить (аккаунтный X25519 да, Ed25519 нет); как новое устройство отдаёт `device_sign_pub` одобряющему.
4. **Политика авторизаторов** — какие устройства могут авторизовывать новые.
5. **UX safety-number** по аккаунтному ключу (ортогонально; покрывает инъекцию, НЕ отзыв).
